# GPU operators

The inference engine's custom kernels are implemented in [kernels.ptx](kernels.ptx).
[cuda.c](cuda.c) is ordinary C host code: it loads an external PTX module through
the CUDA Driver API, obtains five entry points and launches them on the same
nonblocking stream used by cuBLAS. Memory allocation and transfers use the CUDA
Runtime C API. Context destruction drains the stream before unloading the module.

Kernel entry points and argument order:

- `vi_add(x, y, n)`: in-place residual/bias addition.
- `vi_norm(x, weights, out, n, epsilon)`: RMSNorm, with the original serial reduction.
- `vi_rope(x, heads, dim, position, theta)`: in-place half-split RoPE.
- `vi_attention(q, keys, values, out, scores, heads, kv_heads, dim, length, capacity)`.
- `vi_swiglu(gate, up, n)`: in-place SwiGLU.

Pointers and size arguments use the module's 64-bit ABI; epsilon and theta are
FP32. The module targets `sm_80` and requires a compatible GPU and PTX-capable
driver. `linear` retains `cublasSgemv`, pedantic math and disabled atomics.
Launch geometry, stream ordering and floating-point instruction order are
preserved from the previous CUDA backend. There is no CUDA-kernel fallback.

The initial PTX instructions were generated by NVCC 12.8.93 with
`-O2 --fmad=false -arch=sm_80`. Kernel symbols were made stable and visible;
instruction bodies were preserved. The source provenance is recorded in the
PTX header. Edit this PTX file for subsequent kernel changes.

## Build and run

From the repository root:

```bash
./dev run --rm engine generate --model smollm2 --prompt "What is the capital of France?" --max-new-tokens 32
```

The GPU backend is built with the C compiler and CUDA headers/libraries; it does
not compile CUDA C++ or invoke NVCC. Make copies `kernels.ptx` to
`$BUILD_DIR/ptx/model_ops_cuda.ptx`. At runtime, `cuda.c` uses `cuModuleLoad` to
load that file from `ptx/model_ops_cuda.ptx` beside the executable, independently
of the working directory. Deploy the executable together with this `ptx/`
directory. The GPU driver compiles the PTX when loading it.

Set `VI_PTX_PATH` to load another module, for example:

```bash
./dev run --rm -e VI_PTX_PATH=src/model_executor/ops/kernels.ptx engine generate --model smollm2 --prompt "What is the capital of France?" --max-new-tokens 32
```

An explicit relative path is resolved against the working directory. A missing
or invalid module, or a missing kernel entry point, fails initialization with an
error. There is no fallback to an embedded module. PTX edits only require staging
the file again (`make cuda-ptx` or the usual build), with no host recompilation.
The test targets set `VI_PTX_PATH` because their binaries live in subdirectories.
Launches return asynchronously; synchronous reads and writes retain their
original completion checks.

## Regression tests

```bash
./dev run --rm engine make test model-test gpu-ops-test
```

The optional `gpu-ops-test` target requires NVCC to build the frozen, test-only
[CUDA reference](../../../tests/support/cuda_reference.cu). It compares all five
PTX kernels and cuBLAS/bias composition byte for byte, with varied dimensions,
tail blocks, in-place addition, guard regions and invalid-size checks.
The reference CUDA implementation is not linked into the inference engine.
`model-test` also checks executable-relative loading after relocation, explicit
absolute/relative paths, and rejection of missing, malformed or incomplete PTX.

These are execution tests. The NVCC-generated instruction forms in this module
are not yet all supported by `tools/ptx-verify`; no Lean proof is claimed by this
migration.
